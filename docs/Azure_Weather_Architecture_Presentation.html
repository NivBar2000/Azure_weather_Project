Security architecture07
זמינות וגדילה

אין מכונות שמנוהלות ידנית

השירותים מנוהלים על ידי Azure. אנחנו מגדירים capacity, scaling וגבולות כשל.

2–4App Service workers. מינימום 2, autoscale עד 4
2 AZPostgreSQL primary + standby ב-Zones שונים
7 daysתקופת גיבוי למסד הנתונים
1 RegionSweden Central. אין DR אזורי מלא
Front Door ו-App Service מספקים ניתוב ואיזון עומסים. אין ALB או Load Balancer שמנוהל בנפרד.
  • Scale-out מעל 70% CPU במשך 5 דקות
  • Scale-in מתחת 30% CPU במשך 10 דקות
  • PostgreSQL מבצע failover לשכפול standby
  • Storage הוא LRS ולכן אינו פתרון Multi-Region
Availability model08
Terraform

מי מנהל מה?

Terraform מנהל

  • Azure resources ורשתות
  • Managed identities ו-RBAC
  • Diagnostic settings ו-autoscale
  • Front Door routes ו-custom domain association
  • Container Apps migration job

בעלות חיצונית או ידנית

  • Secrets והערכים שלהם
  • Namecheap DNS
  • Entra tenant, app registrations ו-redirect URI
  • GitHub Environment והפעלת Production CD
  • Build artifacts ו-container image של כל release
הפרדה מכוונת: Terraform שולט בתשתית, וה-CD שולט בגרסת האפליקציה. Lifecycle ignores מצומצמים מונעים משני הכלים להילחם זה בזה.

מה בחרנו, ולמה?

Human-in-the-loop

שיטת העבודה עם AI

AI שימש כשותף הנדסי מתועד. האדם נשאר בעל הסמכות על סודות, תשתית חיה ו-Production.

הגדרת משימה וגבולותמטרה, קבצים מותרים, פעולות אסורות וסודיות
שינוי קטן וממוקדInteraction ממוספר לכל החלטה או תיקון
Validation אוטומטיformat, lint, tests, build, Terraform validate ו-diff checks
Human reviewבדיקת התוצאה, plan, rollout והתנהגות Production
תיעוד והפקת לקחיםprompt, response, שינויים, אבטחה, הנחות וסטטוס סופי

דוגמאות לתיקונים שה-AI עזר לזהות

  • OIDC subject עבר לזהויות GitHub immutable
  • שם migration job קוצר למגבלת Azure
  • validation לסיסמת PostgreSQL תואם למציאות
  • tag drift של Azure טופל ב-lifecycle ממוקד
  • הדומיין החדש נפרס בשני שלבים מבוקרים
העיקרון: AI מציע ומבצע עבודה תחומה. CI, Terraform plan והאדם מוכיחים שהתוצאה נכונה.
